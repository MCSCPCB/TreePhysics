# 原型机性能等价审计

> 审计基线：`dcef5486334ec78d9f24bfa688312723da1a7382`。本轮修改保持三次
> `1/60s` 子步、现有碰撞形状、质量/惯量、液体、破碎、伤害、拖拽、活塞、爆炸和持久化语义。

## 结论

当前正式实现并不是因为 Cannon 内核本身大幅退化而慢。已有同进程对照表明，当前基础
Cannon 刚体内核只比归档内核慢约 `5%-6%`。真正的差异来自正式项目在每个活动 tick
执行的世界同步、三子步求解和树木生命周期，而原型机主要依靠跨 tick 的 8x8x8 世界快照、
静态网格复用和单次 `1/20s` 步进绕开了这些成本。

因此，单独把 `Dimension.getBlock()` 叫作瓶颈并不准确。当前路径已经优先用
`Dimension.getBlocks()` 找出非空气候选；高成本是“范围计算 -> 批量查询 -> 候选方块读取 ->
精确形状/材质解析 -> 网格化 -> Cannon 静态体维护 -> 三子步接触求解”这条完整流水线。

本轮完成后，静止装配体已经获得原型机级别的空转成本；活动装配体则能明显接近原型机，
但在纯 Bedrock SAPI 条件下，无法同时保证任意世界修改当 tick 生效、保持全部现有玩法和
达到原型机的活动刚体吞吐量。要绝对达到后者，需要引擎提供可靠的区块 revision/全量方块
变更事件，或把物理和世界快照下沉到原生层。用周期校验代替当 tick 校验虽然能达到原型机
速度，但本质上重新引入了原型机的准确性牺牲，本项目不采用。

## 等量性能为何不同

| 路径 | 原型机 | 当前正式实现 | 性能影响 |
| --- | --- | --- | --- |
| 世界碰撞 | 8x8x8 快照和静态网格跨 tick 复用 | 活动体每 tick 读取当前世界并重建逻辑布局 | 当前更贵，但能响应实时世界变化 |
| 时间步 | 通常每游戏 tick 一次 `1/20s` | 每游戏 tick 三次 `1/60s` | 当前求解成本约为三倍，快速碰撞更稳定 |
| 方块形状 | 以整方块为主 | 支持台阶、门、栅栏等状态/邻居/上下文形状 | 当前解析和网格种类更多 |
| 液体 | 无完整水/岩浆耦合 | 浮力、阻力、入水/岩浆事件和销毁 | 当前需要液面采样和附加力 |
| 树木玩法 | 原型验证所需的最小集合 | 破碎、掉落、伤害、拖拽、活塞、TNT、恢复等 | 当前有额外生命周期成本 |
| 睡眠维度 | 无活动刚体时跳过 | 旧正式实现仍进入内核；本轮已消除 | 本轮后基本等价 |
| 视觉写入 | 较宽松的变换阈值 | 旧正式实现接近浮点逐帧写入；本轮已合并 | 减少 SAPI teleport/property 写入 |

## 原型机为性能牺牲的内容

1. 世界快照在失效前不是当前 tick 的世界真值。命令、自然更新、流体、部分爆炸或活塞变化
   可能暂时使用旧碰撞。
2. 碰撞体主要按完整立方体处理，不能保持当前 partial/state/neighbor/context 形状准确度。
3. `1/20s` 单步比三个 `1/60s` 子步更容易高速穿透、接触抖动和错过短时碰撞。
4. 没有正式版本的完整液体、破碎、伤害、交互、恢复和数据安全成本。
5. 原型阶段的“几十个刚体”不能直接等价为“几十棵带正式树木数据和世界同步的巨树”。

## 本轮实施

1. 所有动态体睡眠且没有回调时，跳过三个 Cannon 子步；环境签名仍按原有 20 tick、支撑仍
   按原有 10 tick 错峰验证，未广播的方块变化仍能唤醒。
2. 睡眠体非验证 tick 完全跳过世界同步；从活动转睡眠时仍清除临时世界碰撞体。
3. 世界碰撞布局变化时按稳定 key 增删 Cannon 静态体，未变化的静态体不再反复销毁重建。
4. 只缓存已证明不依赖状态、邻居和上下文的原版方块碰撞形状。状态方块继续实时解析。
5. 去掉扫描和浮力热路径中的部分短命 `Set`、位置对象和循环数组分配。
6. 脆弱附着物先检查速度再查询世界；当前点与预测点落在同一格时只读一次方块。
7. 通过严格的速度上界证明树木不可能达到起伤速度时，跳过 `Dimension.getEntities()`；
   每 tick 仍更新 swept pose，因此不会漏掉下一 tick 的真实高速冲击。
8. 视觉位置低于 `1/1024` 方块、旋转低于 `0.05` 度时合并写入，变化相对上次已发送值累积，
   不会永久丢失位移；初始、强制、唤醒和最终睡眠同步保持。

## 验证结果

- TypeScript 检查通过。
- Vitest：24 个文件、401 项测试全部通过。
- debug 和 release 构建通过。
- Node 基准中，1230 方块的 10 棵睡眠树约 `0.036 ms/tick`；9800 方块的 10 棵大型
  睡眠树约 `0.106 ms/tick`。静止成本已经主要剩下 Bedrock 实体自身和错峰安全检查。
- 980 方块自动挡位活动树约 `0.458 ms/tick`，5 棵约 `3.124 ms/tick`（Node mock）。
  这证明活动成本仍随装配体、扫描覆盖和形状数增长，实机 SAPI 时间需用 release 包复测。

## 达到原型机要求的现实路径

在两个原则内，当前可执行路径是保留正式物理语义，同时持续减少等价实现开销：睡眠空转、
稳定静态体、静态形状缓存、空实体查询和不可见写入已经完成。下一次实机日志若仍显示活动期
`ws` 占主导，剩余差额属于“每 tick 当前世界权威校验”的平台成本，不应再通过调低子步、
简化碰撞体或跨 tick 缓存来伪装成优化。

只有以下任一前提成立，才能在不违背原则的情况下进一步取得原型机量级的大幅提升：

1. Bedrock SAPI 提供覆盖命令、自然更新、流体、活塞和爆炸的可靠方块/区块 revision；
2. SAPI 提供可直接读取方块类型、状态和碰撞形状的低成本区块快照；
3. 物理扩展迁移到能接收完整世界变更流的原生模块。

在现有 API 下继续做纯分配级优化仍有小幅收益，但不再足以把活动巨树的成本变成只与装配体
数量有关。任何声称可以做到这一点的 SAPI 方案，最终都会在实时碰撞、三子步稳定性、partial
形状或现有玩法中至少牺牲一项。
