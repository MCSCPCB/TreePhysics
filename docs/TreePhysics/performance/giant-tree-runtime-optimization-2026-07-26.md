# 巨型树活动期性能专项

## 实机证据

本轮以 2026-07-26 的 Bedrock 实机日志为依据，不再把 Node mock 计时当作最终结论。

| 树种 | 方块 | 视觉实体 | Cannon shape | 藤蔓 fragment | 峰值物理步 | 峰值世界扫描 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 巨型丛林木 | 403 | 16 | 31 | 5 | `106 ms` | `64 ms` |
| 巨型云杉木 | 412 | 14 | 2 | 0 | `48 ms` | `25 ms` |

丛林木单树日志中，逻辑世界扫描量最高达到 `4397` 方块/tick；云杉木约为
`1760` 方块/tick。两者都表明主要 TPS 峰值位于活动刚体附近的世界方块读取，而不是
Cannon shape 数本身。丛林木另有 5 个藤蔓 fragment，旧路径每个会激活 27 个控制器，
合计 135 个活动控制器，因此它还叠加了明显的客户端 FPS 压力。

测试期间出现的 `Out of memory exception` 只在 `/script profiler start` 长时间持续开启时发生；
同一项目以往关闭 profiler 的长期运行没有该问题。本轮不把它归因于装配体生命周期泄漏。profiler
只应用于短采样窗口，采样完成后立即停止；常规耐久和内存测试必须关闭 profiler。

## 已实施优化

### 原生批量世界扫描

活动 collider 扫描仍每个物理 tick 读取当前世界，不缓存跨 tick 方块，也不缩小保守碰撞范围。
变化只在 SAPI 访问方式：

1. 用 `Dimension.getBlocks(BlockVolume, { excludeTypes: ["minecraft:air"] }, true)` 一次筛出
   当前加载范围内的非空气候选。
2. 只对候选位置调用 `getBlock()`，随后仍用原有液体、sensor、材质和完整/部分碰撞形状解析。
3. 稀疏 shape 并集之外的候选在读取前过滤，不会因为批量 API 使用包围体而扩大物理碰撞范围。
4. `getBlocks()` 调用、返回或迭代任一阶段抛错时，丢弃整批临时结果并在同 tick 完整回退逐坐标扫描。
   不会使用半批数据，也不会生成重复 collider。
5. 第三个参数允许跳过未加载区块，与旧路径中 `getBlock()` 对未加载位置返回 `undefined` 的语义一致。

该方案不改变碰撞结果和物理频率，主要削减 JavaScript 与原生宿主之间的跨边界调用。区域内部仍需由
Bedrock 扫描，非空气候选仍需读取真实 `Block`，因此收益取决于活动 AABB 的空气稀疏度。

### 自适应 shape 并集

两个及以上 shape 不再用固定 shape 数阈值决定扫描方案。内核同时计算完整 body AABB 体积与真实
shape 行区间并集体积，并计入每个 shape 的固定管理成本；只有并集成本严格更低时才使用稀疏方案。
这使巨型云杉的两个长柱 shape 也能避开旋转后大 AABB 中的空白，同时让紧凑刚体继续走低成本密集路径。

### 低 shape 真实候选过滤

最终诊断显示，巨型云杉关键帧的 shadow 可排除 `41%-48%` 非空气候选，自身成本只有 `2-3 ms`；
巨型丛林木仅排除 `19%-27%`，其 `19-23` 个 shape 反而令判断消耗 `5-7 ms`。因此正式路径只在以下
条件全部成立时原地过滤候选数组：不超过 4 个 Cannon shape、预测扫描体积至少 256、批量 API 完整
成功、coverage 内非空气候选至少 256。任何不符合条件或与无 shadow cluster 合并的扫描都保持原路径。

过滤只省略几何上不可能接触装配体的逐块 `getBlock()` 和方块形状解析，`sq`、预测范围、Cannon
collider 与 solver 均不变。被过滤位置如果恰好是非碰撞树叶的浮力点，会执行有界补读；水、岩浆、
partial block、sensor、极端角速度及 batch 调用/iterator 失败均有回归。高 shape 丛林木在诊断关闭时
不创建 shadow shape，也不遍历候选，因此不会承担这项优化的额外成本。

### 休眠巨树世界验证补充优化

静止实机反馈触发了对 `a=0/1` 真正休眠路径的补充审计。此前虽然已经把休眠环境检查从完整 AABB
改为逻辑 shape 稀疏并集并按 body ID 错峰，但每 20 tick 的环境签名仍逐坐标调用 `getBlock()`；每
10 tick 的支撑检查还会在确认支撑存在之前无条件把支撑范围加入 world collider 扫描。后者会让稳定
休眠树周期性创建临时 collider，并在后续 tick 再清空。

正式路径现做两项无损修正：

1. 休眠环境 coverage 至少为 256 个坐标时，复用活动扫描的
   `Dimension.getBlocks(BlockVolume, exclude air, true)` 快路，只对 coverage 内非空气候选读取真实
   `Block`。候选按旧逐坐标路径的线性 index 排序后再生成签名，因此 iterator 顺序、批量成功与回退
   路径不会改变签名。调用或 iterator 中途失败时，同 tick 完整回退旧扫描。
2. 支撑检查先调用原有 `findWorldSupportInBounds()`。支撑存在时不加入 world collider cluster；只有
   支撑消失、body 已唤醒时才加入相同支撑范围，保证唤醒首 tick 的扫描范围与旧路径一致。

固体新增/删除、液体、局部碰撞方块、sensor、批量调用失败和 iterator 失败均有回归。30 格高的单柱
测试覆盖在批量成功时只执行 1 次批量查询和 1 次候选 `getBlock()`；稳定休眠 25 tick 内 collider 数和
rebuild 数始终为 0。现有 Node benchmark world 不实现 `getBlocks()`，因此强制走最坏回退路径；同一
980 方块休眠树的 `qmax` 仍由此前的 `2996` 降到 `2658`，仅删除冗余支撑 collider 扫描便减少约
`11.3%` 查询。Bedrock 的额外批量收益仍以 release 实机 TPS 为准。

### 藤蔓统一色控制器

普通单一群系内的默认 foliage colormap 是统一像素色。此时每个藤蔓 fragment 现在只激活基础 pass
和 1 个统一 colormap pass；26 个逐槽渐变 pass 仅在跨颜色梯度时启用。几何、方向、透明度、方块数、
实体数和最终颜色不变。

因此日志中的 5 个统一色藤蔓 fragment，活动控制器理论值由 `5 x 27 = 135` 降为约 `5 x 2 = 10`。
附件裁剪判定仍按最坏渐变路径将藤蔓计为 27，`[TP:A] ac` 也仍显示保守成本；这避免同一棵跨群系树
因为生成位置不同而失去原有保护。

## 诊断字段

`[TP:P]` 保留原字段，并新增：

| 字段 | 含义 |
| --- | --- |
| `sq` | 保守扫描覆盖的逻辑方块数；用于确认物理范围没有缩小 |
| `sr` | collider 扫描实际执行的 `getBlock()` 次数 |
| `bc` | 原生 `getBlocks()` 返回的非空气候选数，含随后被稀疏 coverage 排除的候选 |
| `bq` | 原生 `getBlocks()` 调用次数 |
| `sa` | 正式应用 shadow 过滤的 cluster 数；云杉目标为非零，丛林木目标为零 |
| `sh` | shadow 保留/排除的 coverage 内非空气候选数 |
| `sd` | shadow 判断自身耗时 |
| `eq` / `sleep_queries` | 当前 tick / 600 tick 汇总的休眠环境与支撑查询量 |
| `ws` | 完整世界 collider 同步耗时，仍是实机最终判断依据 |

批量路径成功时，`sq` 可能与旧日志接近，这是刻意保持物理覆盖的结果；正式 shadow 应表现为 `sa>0`
且 `sr=sh` 的保留数。若原生 API 异常并回退，会看到 `sa=0`、shadow 计数清零且 `sr` 接近 `sq`，
同时玩法仍正确。

## 安全边界与暂不实施项

- 不降低 Cannon 的 3 个子步、solver 迭代、碰撞 shape、浮力点或易碎 sensor。
- 不减少任何主体、原木、树叶或附件视觉；不增加实体。
- 不跨 tick 缓存世界方块，不让物理使用过期状态。
- 不启用专用藤蔓实体或双层叶片 fragment。它们可能改变实体布局或插值，必须由本轮实机结果证明
  仍有必要后再单独评估。
- 睡眠环境验证仍按原 20 tick 频率错峰执行；只改变访问方式，不缓存跨 tick 方块内容。稳定支撑检查
  仍按原 10 tick 频率执行，但不再生成无用途的临时 collider。

## 实机验收

关闭 script profiler 后，分别复测单棵巨型丛林木、单棵巨型云杉木、两棵同时倒伏以及一静一动。
使用 `/scriptevent tree_physics:tree_perf_debug on` 记录 `[TP:A]`、连续 `[TP:P]`、平均/P1 FPS、
平均 TPS 和内存稳定性；完成后用同一事件的 `off` 关闭诊断。2026-07-26 的最终诊断层除每 40 tick
样本外，还使用固定 600 tick 窗口输出 P50/P95/P99/max 并立即清空，不保存无界历史。字段和测试矩阵
见 `final-runtime-bottleneck-audit-2026-07-26.md`；不要同时长期开启 script profiler。

验收要求：树木集合、视觉颜色、运动轨迹、碰撞、浮力、破碎、掉落与恢复均无差异；`sq` 不因优化被
人为压低；空气稀疏场景的 `sr` 显著低于 `sq`；巨型丛林木统一色藤蔓不再同时激活 26 个逐槽 overlay；
`ws` 峰值与卡住后跳帧现象明显改善。只有仍存在可稳定复现的客户端瓶颈时，才进入专用藤蔓或叶片布局阶段。
