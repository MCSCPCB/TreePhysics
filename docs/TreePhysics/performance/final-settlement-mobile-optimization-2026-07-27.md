# 移动端最终结算优化

## 实机结论

移动端在普通三原木树最终转为掉落物时也会出现严重 TPS 下降，而活动期间树叶批量破碎没有同类问题。
两条路径使用相同的 LootTable、粒子、物品生成和树状态持久化；差异来自旧最终结算把 20 tick 上限当作
目标时长，逐操作推进 `runJob` cursor 并反复重写状态。该协议对小树也会制造持续事务成本。

## 当前语义

最终结算先持久化 `pendingSettlement`，确认后删除物理与视觉装配体，并在同一个同步批次中完成副作用：

- 剩余操作数不超过 64 时，每个 LootTable 输出保持对应方块的最终世界位置；
- 超过 64 时，兼容物品按原版最大堆叠量合并，并集中到剩余装配体方块包围盒下表面中心；远处裁剪附着物不参与锚点计算；
- 集中模式仍在原方块位置播放破碎粒子，但确定性采样至最多 32 次；
- 蜂巢蜜蜂仍在蜂巢的最终位置生成；
- 每棵树只播放一次最终完成声音。

最终结算不再使用 `runJob`、`settlementCursor` 或逐 tick JSON 状态重写。恢复中的 pending 记录直接执行
同一批次，不创建临时装配体；逐位置或集中批次 tag 用于跳过仍存在的已生成实体。高成本植被附件的
砍伐期裁剪 job 不属于最终结算，继续保留其独立 cursor 和提交协议。

## 安全边界

`pendingSettlement` 必须在装配体移除和掉落生成之前落盘，因此强退重进不会把待结算记录恢复成物理树。
完成批次后才删除树 manifest/state/structure。SAPI 不提供跨动态属性和物品实体的原子事务；物品已被
玩家拾取后再强退仍不存在数学上的 exactly-once 保证，这一平台边界与原实现相同，但不再存在长达
20 tick 的逐操作暴露窗口。
