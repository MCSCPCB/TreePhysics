# PhysicsAPI 全面性能审计、优化计划与实施报告

## 1. 审计范围与结论

审计基线为 `5753915`，日期为 2026-07-24。范围覆盖 `src` 的树木选择、装配创建、
Cannon 求解、世界方块扫描、树叶物理、实体伤害、持久化、fragment 渲染、掉落物、蜜蜂、
音效和粒子，并检查对应 BP/RP 资源、测试、历史性能文档和构建产物。

结论分为两部分：

1. **持续物理主循环已经没有一个可在完全保持当前物理质量的同时再获得数量级收益的热点。**
   当前生产路径已经把树叶移出 Cannon compound，自动质量档会聚合树叶浮力与接触探针，
   世界扫描使用稀疏 shape AABB 并集，休眠树错峰验证，生命周期合并实体查询，持久化按树分区
   且只写 dirty 记录。最终测量中，5 棵 980 方块大树的生产质量档物理均值为
   `1.9285 ms/tick`，10 棵 980 方块树的生命周期均值为 `0.3560 ms/tick`，相对 20 TPS 的
   `50 ms/tick` 预算仍有明显余量。
2. **本轮找到并完成了客户端粒子、fragment 每帧求值、渲染实体、掉落实体和若干服务器峰值/常数优化。** 最新粒子路由会为每次
   方块效果创建 43 个候选子 emitter，只让其中一个真正激活；Cannon 的 3 个子步又可能对
   同一接触重复调用该路由。这是粒子加入后出现的新热点。大型树的同步选择与装配也分别达到
   约 `20 ms` 和 `16 ms`，适合做严格无损的算法常数优化，但不能直接跨 tick 改写事务边界。大型丛林木
   的新增 FPS 热点不是 Cannon 或实体数量重新失控，而是少量大 fragment 仍让客户端每帧进入大量
   render controller、Molang 属性解码和骨骼可见性表达式；两棵树同时运动时，客户端帧延迟又会使
   20 TPS 的服务端姿态更新看起来像“直立停住后瞬间倒地”。

本轮优化集中在粒子路由、重复碰撞事件、自适应 fragment 布局、客户端条件控制器与属性预解码、
`low` 树掉落堆叠、建树扫描常数、休眠同步和长期缓存。没有降低物理子步、删减碰撞、限制树木数量、
隐藏视觉方块或减少掉落总量。

## 3. 分系统审计

### 3.1 物理解算与世界碰撞

当前每游戏 tick 使用 3 个 `1/60 s` Cannon 子步。原木和附件保留真实 compound，树叶逻辑质量、
质心、惯性和浮力仍存在，但生产路径不再给每片树叶创建 Cannon shape。自动质量档下，980 方块
大树只有约 2 个生产 collider shape；对照 exact 路径为 57 个 shape。5 棵大树由 exact 的
`9.87 ms` 降到 auto 的 `1.89 ms`。

不能实施的所谓“优化”：

- 把 3 子步降为 1 子步：会改变碰撞稳定性、落地视觉、冲量和穿透概率。
- 跨 tick 缓存活动树附近方块：会让物理使用过期世界状态，影响易碎方块、活塞和玩家放置。
- 删除原木/附件 shape 或降低世界扫描范围：直接降低物理质量和玩法正确性。
- 按负载动态改变已经创建的树木质量档：会产生同一棵树运行中语义漂移。

实时读取当前世界是正确取舍。2026-07-26 的后续实机诊断证明，保持相同逻辑覆盖时仍可通过
`Dimension.getBlocks()` 原生非空气预筛选减少宿主边界调用，再对候选执行相同 `getBlock()` 和碰撞
解析；异常时完整回退旧路径。该专项见 `giant-tree-runtime-optimization-2026-07-26.md`。

### 3.2 Bedrock SAPI 调用

高成本宿主调用集中在：

- 活动世界碰撞的 `Dimension.getBlocks()` 与候选 `Dimension.getBlock()`，以及浮力补充读取；
- 砍伐前同步树扫描的 `Dimension.getBlock()`；
- fragment 创建时的 `spawnEntity()` 和 `setProperty()`；
- 碰撞/破碎的 `spawnParticle()`；
- 掉落的 loot 计算与 `spawnItem()`；
- 伤害查询的 `Dimension.getEntities()`。

现有代码已经合并伤害查询、错峰持久化与休眠扫描。新增的无损机会是：同一个 Cannon tick 内，
同一世界坐标被多个重复接触读取时复用该 tick 的 `Block` 结果；缓存绝不跨 tick，也不用于活动
物理世界扫描，因此不会产生过期物理状态。

### 3.3 渲染实体数量与 FPS

fragment 已经把一方块一实体的服务端/SAPI 压力降了两个数量级：

- 123 方块标准树：123 个旧显示实体降到 3 个 fragment 实体，原本为 5；
- 980 方块大树：15 个 fragment 实体，原本为 19；
- 10 棵标准树：1230 个旧实体降到 30 个 fragment 实体，原本为 50；
- 每棵树的所有 fragment 共享同一世界锚点，移动时 transform 写入量等于 fragment 数，不等于方块数。

这也解释了与一方块一实体方案的症状差异。旧方案首先耗尽服务端实体 tick、属性同步和脚本调用预算，
所以主要掉 TPS；fragment 方案把实体数降下来后，剩余成本集中到少数实体的客户端 render controller、
Molang 和骨骼可见性求值，所以单棵大型丛林木也可能先掉 FPS。FPS 足够低时，服务端仍按 20 TPS 推进，
客户端来不及呈现中间插值帧，最终就会看到装配体直立卡住，然后跳到已经落地的状态。两棵树或一动一静
时，客户端资源线程与脚本/同步压力叠加，才会进一步拖累集成服务器 TPS。

原 `7x4x7` 原木 fragment 使用 196 槽和 25 个 24-bit 数据字；新增 `5x10x4` 高干 variant 使用
200 槽和相同 25 个数据字。加入 2-bit `modes` 后两者都正好使用 32 个同步属性，geometry 分别为
201/205 根骨骼，仍不超过 32 属性、256 骨骼的门槛。打包器对每个原木 family 同时计算宽枝和高干布局，
只在实体数严格更少时选择高干布局，因此宽枝树绝不因本轮优化增加实体。正式 benchmark 中标准树原木
由 3 个降到 1 个，
980 方块树原木由 7 个降到 3 个。

本次 FPS 专项采用以下不增加运行时实体、也不改变可见方块的方案：

1. 原木同步属性增加 `modes` 位图。只有普通原木时只进入 side/top 两个普通控制器，只有去皮原木时
   只进入两个去皮控制器；混合分片才保留四个。删除最后一个对应槽时运行时立即重算位图。
2. 附件使用 `origin_y` 的低 11 bit 保存原 Y，高位保存 9 个 attachment family 的存在位图，不占用
   新同步属性。新分片只进入实际存在 family 的控制器；mask 为 0 时临时回退为全部控制器，保证更新前
   已存在的视觉实体不会消失。删除最后一个 family 槽时位图同步更新。
3. 原木的 25 个 `s*`、叶片的 `l*`、附件的 26 个 `a*` 以及 family/state/present、染色坐标都在
   `pre_animation` 每帧各读取/解码一次，后续动画与控制器只读 `v.*`。以 196 槽原木为例，生成资源中
   槽状态的同步属性读取表达式由每槽在动画/四控制器中重复出现，收敛为 25 次预读；这属于静态资源
   表达式数量变化，最终 GPU/CPU 时间仍由 Bedrock profiler 确认。
4. 保留 `7x5x7`、245 槽叶片，新增单层 `6x5x6`、180 槽、8 数据字、15 同步属性、185 骨骼的紧凑
   variant。只有紧凑布局实体数不增加且总槽容量更小时才采用，因此每个叶片实体的可见性槽位最多
   下降 26.5%，绝不会为了减 Molang 而增加实体。染色仍按该 variant 的真实 6x6 footprint 采样。
5. 无 colormap 的叶片不再进入第二个 multiply pass；有 colormap 时仍完整执行原 base + multiply
   两遍，颜色与透明视觉不变。

附件资源一共声明 68 个控制器和 2652 条非根可见性条件。仅含藤蔓的 fragment 现在只进入 27 个
控制器、260 条条件，控制器数下降 60.3%，可见性条件下降约 90.2%；同时含 cocoa 与 vine 时为
30 个控制器、338 条条件。未出现的 bee nest、roots、moss、heart 等 family 不再为每帧付费。
这些是资源结构可直接计数的上限削减，不等同于已经测得 90.2% FPS 提升。

没有启用“每个 fragment 使用独立世界锚点并收紧 visible bounds”。共享锚点由客户端连续插值；如果
每个分片在 20 TPS 上分别 teleport，虽然数学姿态一致，帧间插值仍可能不同步，造成整棵刚体撕裂。
也没有发布 `7x10x7` 双层叶片候选：它虽可减少实体，却会增加大树总可见性条件。两者必须先按第 5 节
做 Bedrock A/B，不能以潜在视觉退化换 FPS。

可无损优化：已经稳定休眠且上一 tick 已同步最终姿态的树，直接跳过重复欧拉角、锚点和字符串
比较；唤醒或强制同步时立即恢复完整路径。

### 3.4 大型树木构建

树选择发生在 `beforeEvents.playerBreakBlock`。必须在原世界树仍存在时完成归属、自然根、人工树、
叶距和附件判定；事件返回后原方块可能已被破坏。因此不能简单把它改为 `runJob()`。

装配创建也采用“先创建完整物理/视觉对象，再事务删除世界树”的顺序。跨 tick 分批生成 fragment
会在世界树仍存在时产生重叠视觉，或在先删世界树时产生缺失视觉；中途退出还会扩大恢复窗口。
在不新增隐藏阶段实体协议与持久化事务前，不做这种改写。

本轮实施一个严格等价的扫描优化：候选叶片洪泛已经读取了所有原木和距离小于 6 的叶片邻域，
附件收集不再为每个 source 重做 26 邻域字符串查找；改为遍历 reader 已捕获的附件并反向查询相邻
source owner，仅对最大叶距边界补读邻域。归属规则仍取最先的 component，世界查询结果和方块集合不变。

质量档选择还有一个确定性快路：叶片超过 2048 时，无论精确 mesh 的 box 数和当前活动预算如何，
结果都只能是 `low`。原实现仍会先尝试 6 种轴序的精确 mesh；单独测量 4096/6144 叶片约需
`35-44 ms` / `58-70 ms`。现在直接创建完全相同的 `low` 计划；恢复已持久化质量档或显式指定质量档
时也不再计算从未读取的 exact box 数。叶片分组、浮力点、接触探针和运行时物理表示均不改变。

### 3.5 掉落物、蜜蜂与最终结算

2026-07-27 的移动端实测证明，即使普通小树，旧版逐操作 `runJob`、cursor 和反复持久化也会形成明显
TPS 低谷。最终整树结算现改为单批事务：先持久化 `pendingSettlement`，再移除物理树并一次性计算全部
原版 LootTable。最多 64 个剩余方块在各自最终世界位置生成；超过该规模时，使用
`ItemStack.isStackableWith()` 合并组件完全兼容的同类物品，遵守 `maxAmount`，并集中到最终包围盒
下表面中心。巨型集中结算的破碎粒子确定性采样至最多 32 次，原位置、类型和染色仍然保留。

最终结算不再保存 `settlementCursor`，也不再调用 `runJob`。恢复时 `pendingSettlement` 阻止重建装配体，
批次或逐位置实体 tag 用于跳过极窄中断窗口内已有的掉落。掉落总数量、种类、组件、蜂巢蜜蜂数量和
工具附魔 LootTable 语义不变。高成本附件的砍伐期裁剪仍是独立的持久化 job；活动期间的 `low` 叶片/
附件批次也继续使用原有 `>16` 合并规则。

### 3.6 音效

- 木材碰撞声：每 body 至多每 8 tick 一次；
- 一批树叶/附件破碎：整批一次，音量按数量缩放；
- 整树结算：完成后一次。

进一步合并不同树的空间音效会破坏方向与距离信息。当前不存在值得做的音效数量优化。只需清理
长期失效 body 的碰撞冷却记录，避免长时间服务器内存缓慢增长。

### 3.7 粒子

当前碰撞路径为：

`spawnParticle(tree_dust_entry)` -> `tree_dust` + `tree_collide` router -> 43 个类型 emitter。

当前破碎路径为：

`spawnParticle(tree_block_destruct)` -> 43 个类型 emitter。

最终只有一个类型 emitter 的 `activation_flag` 为 1，其余为空 emitter。一次碰撞会创建约 45 个
emitter 层级，一次破碎会创建约 44 个层级；大量叶片连锁破碎时客户端开销被放大约 43 倍。

本轮让脚本根据已经解析出的 visual family/state 直接选择
`tree_physics:tree_collide_<type>` 和 `tree_physics:tree_block_destruct_<type>`。碰撞仍同时产生 6 个 dust
粒子和原数量的方块碎片；破碎仍产生原来的 27 个碎片；位置、纹理、颜色、生命周期、速度和碰撞
参数不变。直接 effect 需要设置 `activation_flag=1` 以及标量颜色变量。

同 body、同 Cannon tick、同装配体方块、同 1/16 方块量化接触点的重复碰撞粒子只播放一次；不同
接触点仍分别播放。这只消除 3 子步/持续 contact 造成的重叠副本，不裁剪独立可见接触。

水花只在 `inWater` 从 false 变 true 时产生一次，当前最多 400+400 个水面粒子并按接触面积缩放。
它是单次高视觉效果，不存在重复路由，保持不变。

### 3.8 实体伤害、持久化和长期内存

活动树的伤害 AABB 已按维度合并，10 树/32 共享候选的生命周期均值仍约 `0.11 ms`。伤害只检查
带 health 的非物品、非显示实体，4 tick 冷却，当前无大块空间。

分区持久化将结构与动态状态分开，活动/休眠树按 body ID 错峰，结构只在变更时写。10 棵 980 方块
树的序列化数据约 3.2 MB，但 steady tick 均值仍低；不恢复全量 JSON 每 20 tick 重写。

人工树 chunk cache 和碰撞音效 body cooldown 是长时间运行的增长点。本轮给人工树缓存增加有界 FIFO
淘汰；数据仍保存在 dynamic properties，淘汰只释放内存。碰撞冷却按仍存在的 body 周期清理。

## 4. 实施工作包

### P0：粒子直达与重复接触合并（已完成）

1. 用 family/state 生成最终 particle suffix。
2. 直接播放 typed collide/destruct effect，设置 `activation_flag` 与标量颜色。
3. 碰撞额外直接播放 `tree_dust`，保持原 6 个烟尘粒子。
4. 为同 tick 同接触建立短生命周期 key，去掉重复子步副本。
5. 为碰撞世界方块读取建立仅当 tick 有效的缓存。
6. 单测验证 exact effect ID、颜色、dust 以及相同/不同接触去重。

实现后的结构结果：破碎从约 44 个 emitter 层级降到 1 个；单个唯一碰撞从约 45 个降到 2 个；三个重复子步

## 6. 最终边界判断

本轮已完成所有能证明语义等价且收益值得复杂度的优化。标准树视觉实体由 `5 -> 3`，980 方块树由
`19 -> 15`；运行时实体数不增加的前提下，又加入条件控制器、属性预解码和 180 槽紧凑叶片；仅藤蔓
附件分片的静态可见性条件上限由 2652 降到 260。破碎/唯一碰撞/重复三子步的 emitter 层级约由
`44/45/135 -> 1/2/2`；大型叶片装配跳过必然无效的 exact mesh；`low` 树高并发掉落按堆叠上限合并
并保留确定性恢复协议。

剩余主要峰值是大型树砍伐前必须同步取得的世界快照、活动破碎的真实 loot 计算和每方块 27 个破碎
粒子。前者受 before-event 事务边界约束；后两者只有改变效果时序或增加 active-break 持久化 journal
才能继续分片，不能用无状态 job 冒充数据安全优化。

持续 Cannon 求解、伤害查询、音效、最终 settlement、原木 fragment 和长期缓存已接近当前语义下的
收敛点。大型丛林木还存在可观的客户端空间，本轮已落地其中无需增加实体、无需改变视觉的部分；实际
FPS 收益必须由 Bedrock 实机平均/P1 FPS 决策。剩余候选是独立锚点/紧 bounds 和叶片双层 variant，
前者可能产生 20 TPS 插值撕裂，后者以大树约 +33% Molang 可见性判断换取 `15 -> 11` 个实体，均不能
只凭离线装箱结果发布。因此，在保持当前玩法、物理轨迹、粒子数量和视觉质量的硬约束下，服务器侧已无
明确的大块优化空间；客户端的安全大块优化已经实施，进一步结构变更属于必须实机 A/B 的风险决策。
